::: Intro / AGENTS.md Hi everyone. This is a short presentation about a few practical things I've learned while using AI as a developer. Some of this you may already know. Some of it is a bit more niche. But the goal is simple: use AI more efficiently, waste less context, and get better results. So first: **AGENTS.md**. An `AGENTS.md` file is basically a markdown file with instructions for the AI agent. The way I think about it is: instead of repeating the same rules every time I open a new chat, I put those rules in a file that the agent can load automatically. There are usually two levels that matter. The first one is the one in your home directory. That one is for general rules that apply to all repos on your machine. Things like: ask before making assumptions, keep changes minimal, don't touch unrelated code, explain uncertainty, stuff like that. Then there is the repo-level `AGENTS.md`. That one is more specific to the project you are working on. For example, if I'm working on TCOMS, there are project conventions, build commands, test commands, important folders, maybe files that should not be touched, and some general explanation of how the repo is structured. That is useful because when you start a new chat, the AI does not remember the previous conversation. So instead of making it rediscover everything every time, you give it a small map of the project. It does not need to search through the whole codebase just to understand where things are or how to build the project. It can start with the important context already available. So the main idea is: `AGENTS.md` is not magic. It is just persistent instructions. But it saves time because you stop repeating yourself, and the agent starts with better context. ::: Skills Just out of curiosity, by show of hands, who already uses skills? Okay, so quick intro. A skill is basically a reusable instruction that you give to the AI. It's usually just a markdown file, kind of like `AGENTS.md`, but instead of being general project rules, it's more like a reusable workflow. For example: PR review, database changes, frontend design, testing, release notes - anything you do more than once. The reason skills are useful is simple: you don't have to re-explain the same workflow every time you start a new chat. You put the instructions once in a skill, and then you can reuse it. And skills become even more powerful when you combine them with tools or CLI commands. The skill can explain the workflow, and the CLI can do the deterministic part. For example, for these slides, I could have just said, "generate me some nice slides." But instead, I used a design-focused skill made by someone who knows frontend/design. So the AI had better design guidance, and the output was much better from a simple command. One important thing: you don't always want a huge skill to dump everything into the context. For example, if I have a big TCOMS skill that covers PRs, database, frontend, testing, and release notes, I don't want the AI to load PR instructions when I'm only working on a database change. So the better pattern is to have a small main `SKILL.md` with a description and a routing table. Then the agent can load only the specific file it needs: `database.md`, `frontend.md`, `testing.md`, `pr.md`, and so on. So the main idea is: skills help you reuse good instructions, but good skills also keep the context small. ::: Agent Hooks Quick show of hands again: who has used hooks before? Okay, so hooks are basically scripts or commands that run automatically at specific moments in the AI agent workflow. There's a source link at the bottom of the slide with more details, but the basic idea is simple: instead of asking the agent to remember every step, you can automate some of those steps. For example, a **SessionStart** hook runs when a new session starts. You can use it to load project state, progress files, a task summary, or anything the agent should always know before it starts helping. Then there is **UserPromptSubmit**. This can run every time you send a message. One use case is attaching task context automatically, so the agent does not forget what feature, branch, or work item you are working on. Then **PreToolUse** runs before the agent uses a tool. This is useful for safety. For example, before the agent runs a terminal command or edits a file, a hook can check if the command is risky, if the file is protected, or if the agent is trying to touch something it should not touch. **PostToolUse** runs after a tool is used. This is very useful for deterministic checks. For example, after editing a file, you can automatically run formatting, linting, or tests. So instead of telling the AI every time, "now run the formatter, now run the tests," the hook handles it. And finally, **PreCompact** can run before the conversation gets compacted. This matters because compaction can lose details. So before that happens, you can save the important state into a markdown file: what was done, what decisions were made, what is still left, and what the next step is. So the main idea is: hooks make the AI workflow more reliable. They reduce manual prompting, they reduce token waste, and they make sure important checks happen consistently. ::: CLI Tools CLI tools. So, what is a CLI tool? It's simply a command-line tool that does repeatable work for you. Usually, that means one of two things: either it runs a sequence of steps, or it wraps checks that you do again and again. The reason this matters with AI is that there are many things we ask the AI to do that are actually pretty deterministic. If we look at the image, the top part shows the manual loop. Let's say CI is failing. You ask the AI what's wrong. Then the AI starts doing the same routine: check the repo, run tests, inspect logs, maybe check another branch, maybe look at the database, maybe inspect a worktree, and so on. Yes, it can do that. But if this kind of task happens often, it becomes inefficient. Why? Because every time, the AI has to reason through the same steps again, call multiple tools, read a bunch of raw output, and then summarize it. That costs time, costs tokens, and it also increases the chance of drift or mistakes. Now look at the bottom part of the image. Instead of asking the AI to figure everything out manually every time, you give it a CLI tool. For example, maybe a run-checks command. That command can do all the deterministic work: run tests, inspect logs, check build status, validate something in the database, maybe check work items, maybe inspect the app state. And then instead of dumping huge raw output back into the AI context, the tool returns a small, clean result. That part is important. One big reason to use CLI tools is not just automation - it's output control. For example, instead of passing 500 lines of logs to the AI, your CLI can return only: the lines containing errors, the failing test summary, a short JSON result like ok, warning, failed, or just the important status fields. So instead of giving the model a wall of noise, you give it compact structured output. That means: less token usage, faster responses, less reasoning wasted on mechanical steps, and usually more reliable results. A real example for me is database work in TCOMS. There are a lot of naming conventions and small validation rules. For example, if there is one foreign key, it has to follow a certain naming rule. If there are two, then the naming changes, and you need to use the role name suffix, and so on. These are not hard things, but they are annoying, repetitive, and mentally draining. That is exactly the kind of thing that should become a CLI tool. So instead of asking the AI every time to remember and re-check all those rules manually, the AI can just call the tool, and the tool gives back the result. And the nice thing is: now that we have AI, creating these little tools is much easier. Before, for a small task, writing a custom CLI might have felt like too much effort. Now you can just ask the AI to build it for you. And once the tool exists, you can call it directly, or even wrap it inside a skill so the whole workflow becomes reusable. So the main idea is: If a task is repeated and deterministic, don't keep making the AI re-reason it. Turn it into a tool. ::: CodeGraph **CodeGraph.** This goes back to the same idea: better context, less noise. Normally, when an AI agent needs to understand a codebase, it often does it the slow way. It searches with grep or ripgrep, opens files one by one, reads a lot of code, and tries to rebuild the structure in its head. That works, but it can be expensive in terms of tool calls, time, and context. CodeGraph does something different. It pre-indexes the project into a local code graph. So instead of only searching text, the agent can ask questions about the structure of the code: functions, classes, methods, imports, dependencies, callers, callees, and impact. In the CodeGraph docs, the main tool is `codegraph_explore`. One call can return the relevant source, the call paths between symbols, and the blast radius of a change. So the idea is not just "search faster." It's more like: give the AI a map of the codebase. That way, instead of reading a bunch of unrelated files, it can get the code that is actually relevant to the question. And this fits with everything I said earlier about context management. Less random code in the context. Fewer unnecessary file reads. Less noise. Better answers. I think this kind of thing, whether it is CodeGraph, LSP, or another code intelligence layer, is probably going to become standard in AI coding tools, because AI agents need structured code context, not just raw text search. ::: Artifacts **Artifacts.** This is about turning the chat into files. When you work on a bigger feature, the AI conversation can get long very fast. You might have the PBI description, the plan, what you already changed, what is left, decisions you made, files touched, branch info, and so on. You don't want to copy-paste all of that every time you start a new chat. So one pattern is to create living documents. For example: `plan.md` for the overall plan, `tasks.md` for the checklist, `progress.md` for what is done and what is still left. These files become a kind of lightweight project memory. The useful thing is that this memory is not trapped inside one chat. A new AI session can read the files and understand where the work is at. You can update these files manually, but this is also where skills and hooks become useful. A skill can define the structure, and a hook can help load or update the files at the right time. There is also a framework called GSD - Get Shit Done - that does this kind of thing more formally. It has a discussion phase, planning phase, task tracking, and saves artifacts as you go. So the main idea is: Don't keep all project memory inside the chat. Turn the useful parts into files the AI can reuse. ::: Plan Review **Plan first, then review with fresh context.** This one is a simple tip about planning. Most AI coding tools now have some kind of planning mode. That is already good, because before the AI starts editing files, you want it to explain what it is going to do. But you can make that process better by reviewing the plan before implementation. The important part is: don't just ask the same agent, in the same conversation, to review its own plan. It can work sometimes, but it is not the best setup. The agent already created the plan, so it may be biased toward its own approach, or it may miss the same assumptions again. A better pattern is to use a separate critic agent, or a sub-agent, with a clean context. You give it only the plan and ask it to look for problems: missing requirements, risky changes, edge cases, test gaps, security issues, rollback concerns, and simpler alternatives. So the first agent is the planner. The second agent is the reviewer. And because the reviewer starts fresh, it is more likely to challenge the plan instead of just agreeing with it. You can even make this reusable with a skill. For example, a "plan review" skill that spawns a critic agent and gives it specific instructions on how to review plans. So the main idea is: Before coding, get a plan. Before trusting the plan, get a second opinion.
